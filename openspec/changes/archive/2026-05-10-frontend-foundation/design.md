# Design: Frontend Foundation & Infrastructure (SM-FE-01)

## Pattern Selection Log

| Pattern | Decision | Rationale |
|---|---|---|
| Database-per-service | Not applicable | Frontend SPA — no database ownership |
| CQRS | Not applicable | No backend read-model projection in this module; all reads are via RTK Query cache |
| Saga (Choreography) | Not applicable | No distributed transactions in the foundation layer |
| Saga (Orchestration) | Not applicable | No saga orchestrator; multi-step flows belong to feature modules |
| Outbox | Not applicable | Frontend does not publish domain events |
| Idempotency | Not applicable | Idempotency-Key header attachment belongs to mutation endpoints in feature modules (SM-FE-02 through SM-FE-06) |
| Timeouts | **Applied** | Every `fetchBaseQuery` call enforces a 10s AbortController-based timeout per PROJECT.md §7 (HTTP read timeout = 10s) |
| Retries with Backoff | **Applied** | `baseQueryWithRetry` wraps `fetchBaseQuery`; retries **GET requests only** on 5xx / 408 / 502–504 up to 3 times with exponential backoff (base 200ms, max 5s, ±30% jitter) per PROJECT.md §7. Non-GET requests (POST, PATCH, PUT, DELETE) are **never retried by default** to prevent duplicate mutations; mutations may opt in via `extraOptions.allowRetry = true` only after SM-FE-02 establishes Idempotency-Key header infrastructure. |
| Circuit Breaker | Not applicable | Circuit breaking for downstream services is enforced by the API Gateway (ADR-006, opossum library); the SPA relies on the gateway's 503/fallback responses |
| Bulkheads | Not applicable | SPA has no thread or connection pools to isolate |
| Cache-aside | **Applied** | RTK Query's normalised in-memory cache implements cache-aside for all API responses; `keepUnusedDataFor` global default set to 60s; per-endpoint TTLs overridden in feature slices |
| Read-through | Not applicable | RTK Query cache-aside already provides read-through semantics on cache miss — no additional pattern needed |
| Write-through | Not applicable | SPA does not maintain a persistent local cache that must stay in sync with the server |
| Cache Invalidation | **Applied** | Tag-based invalidation registry in `baseApi`; every entity type (BOOKING, TRAVELER, EXPENSE, FLIGHT, POLICY) has a pre-registered tag constant so feature modules use consistent invalidation keys |

**Applied patterns**: Timeouts, Retries with Backoff, Cache-aside, Cache Invalidation

**Architectural assumptions**:
- API Gateway handles circuit breaking; SPA only needs to display graceful degradation UI on 503
- RTK Query in-memory cache is cleared on page reload (no persistent cache storage)
- All state is ephemeral (no `localStorage`/`sessionStorage` for app data — auth tokens managed by SM-FE-02)

## Resilience Design

### Timeouts

`fetchBaseQuery` does not natively support timeouts. A custom `baseQueryWithTimeout`
wraps it with `AbortController`:

```typescript
const TIMEOUT_MS = 10_000; // PROJECT.md: HTTP read timeout = 10s

async function baseQueryWithTimeout(args, api, extraOptions) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), TIMEOUT_MS);
  try {
    return await rawBaseQuery({ ...args, signal: controller.signal }, api, extraOptions);
  } finally {
    clearTimeout(timeoutId);
  }
}
```

- On abort: RTK Query receives `{ error: { status: 'FETCH_ERROR', error: 'AbortError' } }`.
- Abort errors are **not** retried (they are treated as permanent failures at the retry layer).

### Retries with Backoff

`baseQueryWithRetry` wraps `baseQueryWithTimeout`:

```typescript
const MAX_RETRIES = 3;
const BASE_DELAY_MS = 200;
const MAX_DELAY_MS = 5_000;
const TOTAL_DEADLINE_MS = 30_000;  // hard cap: no retry beyond 30s total elapsed
const RETRYABLE_STATUSES = [408, 500, 502, 503, 504];
// Safe HTTP methods — only these are retried by default (idempotency guarantee)
const SAFE_METHODS = ['GET', 'HEAD', 'OPTIONS'];

async function baseQueryWithRetry(args, api, extraOptions) {
  const startTime = Date.now();
  let attempt = 0;
  // Determine effective HTTP method (RTK Query args may be string URL or object)
  const method = (typeof args === 'string' ? 'GET' : (args.method ?? 'GET')).toUpperCase();
  const isSafeMethod = SAFE_METHODS.includes(method);
  // Mutations may opt in to retry only when Idempotency-Key infrastructure is in place (SM-FE-02+)
  const allowRetry = isSafeMethod || (extraOptions?.allowRetry === true);

  while (true) {
    const result = await baseQueryWithTimeout(args, api, extraOptions);
    const isRetryable = result.error &&
      (result.error.status === 'FETCH_ERROR' ||
       RETRYABLE_STATUSES.includes(result.error.status as number));
    const isAbort = result.error?.error === 'AbortError';
    const deadlineExceeded = (Date.now() - startTime) >= TOTAL_DEADLINE_MS;

    if (!isRetryable || isAbort || !allowRetry || attempt >= MAX_RETRIES || deadlineExceeded) {
      return result;
    }

    const jitter = 1 + (Math.random() * 0.6 - 0.3); // ±30%
    const delay = Math.min(BASE_DELAY_MS * Math.pow(2, attempt) * jitter, MAX_DELAY_MS);
    await new Promise(r => setTimeout(r, delay));
    attempt++;
  }
}
```

- **GET, HEAD, OPTIONS** are retried automatically (safe/idempotent per RFC 9110).
- **POST, PATCH, PUT, DELETE** are NOT retried by default — prevents duplicate bookings or double-charges if the server processed the request but failed to send a response.
- Mutations may pass `extraOptions.allowRetry = true` once SM-FE-02 ensures an Idempotency-Key header is attached to every mutation request.
- Non-retryable HTTP codes (400, 401, 403, 404, 422) return immediately regardless of method.
- `AbortError` (timeout) is not retried.
- `TOTAL_DEADLINE_MS = 30_000` caps total retry time; no further retry is attempted if 30s has elapsed since the first attempt, regardless of `MAX_RETRIES` remaining.
- After 3 retries (4 total attempts) or deadline exceeded, the last error is returned to RTK Query.

## Caching Design

### Cache-aside (RTK Query in-memory cache)

RTK Query acts as a cache-aside layer: on a cache miss, `baseQueryWithRetry` fetches
from the API Gateway and the result is stored in the normalised Redux store.

| Scope | `keepUnusedDataFor` | Notes |
|---|---|---|
| Global default (baseApi) | 60s | Applies to any endpoint that does not override |
| Flight search (SM-FE-03) | 300s (5 min) | Matches inventory-service Redis TTL |
| Traveler profile (SM-FE-05) | 3600s (1h) | Matches traveler-service Redis TTL |
| Receipts (SM-FE-06) | 86400s (24h) | Receipts are immutable after generation |
| Booking status (SM-FE-04) | 0s | Polling endpoint — never cache |

Cache is in-memory only; page reload clears it entirely.

### Cache Invalidation (Tag-based)

`baseApi` registers all entity tag types up front. Feature slices declare
`providesTags` on queries and `invalidatesTags` on mutations without redefining tag
names.

Example flow (Booking cancel, SM-FE-04):
```
DELETE /bookings/:id
  → invalidatesTags: [{ type: 'BOOKING', id }]
  → RTK Query evicts the cached GET /bookings/:id entry
  → next render triggers a fresh fetch
```

Cache unavailability fallback: RTK Query `isLoading` / `isFetching` states drive
skeleton loaders (`Skeleton` component) until data is available. On error, `EmptyState`
or `Alert` is shown.

## Error Handling

| Error type | Classification | Handling |
|---|---|---|
| 5xx / 408 / 502–504 | Transient | Retried by `baseQueryWithRetry`; if all retries exhausted → dispatch `notificationSlice.addError` |
| 400 / 422 | Permanent | Returned directly to the calling component; field-level errors shown via `FormField` |
| 401 | Permanent | Dispatch `logout` + redirect to `/login` (implemented in SM-FE-02 `baseQueryWithReauth`) |
| 403 | Permanent | Show `EmptyState` with "Access denied" message |
| 404 | Permanent | Show `EmptyState` with "Not found" message |
| AbortError (timeout) | Permanent (no retry) | Dispatch `notificationSlice.addError` with "Request timed out" |
| Render error | Caught by `ErrorBoundary` | Render fallback UI; log to console in dev, to observability in prod |

Global error shape from API (PROJECT.md §9):
```typescript
interface ApiError {
  error: string;
  message: string;
  details?: Array<{ field: string; message: string }>;
  correlationId: string;
  timestamp: string;
}
```

The `correlationId` from API error responses is displayed in snackbar messages to aid
support triage.

## Security Considerations

- **No sensitive data in Redux** — auth tokens managed by SM-FE-02 only; `baseApi` does not
  store tokens (SM-FE-02 attaches the `Authorization` header via `prepareHeaders`).
- **No `localStorage` / `sessionStorage`** for application state — all state is ephemeral
  in Redux (memory).
- **Content Security Policy** — Nginx serves a `Content-Security-Policy` header:
  `default-src 'self'; connect-src 'self' ${REACT_APP_API_URL};`
- **SRI** — Vite production build inlines hashes; no external CDN scripts.
- **Env config** — `window.__ENV__` is served as a static file from Nginx; it contains no
  secrets (only the API Gateway URL which is not sensitive).

## Observability

The foundation layer instruments the RTK Query base query with the following signals:

### Metrics (emitted to `window.__METRICS__` in dev; sent to Prometheus via API Gateway in prod)

| Metric | Type | Labels | Emitted when |
|---|---|---|---|
| `frontend_api_requests_total` | Counter | `method`, `endpoint`, `status_code` | Every `baseQueryWithRetry` final result |
| `frontend_api_retry_total` | Counter | `endpoint`, `attempt` | Each retry attempt |
| `frontend_api_request_duration_ms` | Histogram | `endpoint` | Each completed (or timed-out) request |
| `frontend_cache_hit_total` | Counter | `endpoint` | RTK Query serves from cache (no network call) |
| `frontend_cache_miss_total` | Counter | `endpoint` | RTK Query triggers a network fetch |

### Structured Logging (browser console in dev; forwarded to ELK via Nginx access log in prod)

Required fields per PROJECT.md §8:
```json
{
  "timestamp": "ISO 8601",
  "level": "error|warn|info|debug",
  "service": "frontend",
  "correlationId": "from X-Correlation-ID response header",
  "message": "text",
  "context": {}
}
```

### Retry-specific observability

`baseQueryWithRetry` logs at `warn` level on each retry:
```json
{ "level": "warn", "message": "API retry attempt", "context": { "attempt": 1, "endpoint": "/bookings", "status": 503 } }
```
